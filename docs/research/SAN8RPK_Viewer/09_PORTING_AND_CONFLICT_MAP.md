# Step 09 - S8RPKCheats 이식 후보 정리 및 충돌 지도

## 0. 목적

이 문서는 Step 03~08에서 해부한 Viewer 기능을 현재 S8RPKCheats 코드베이스와 대조해 **나중에 기능별로 이식할 때의 기준표**로 사용하기 위한 문서입니다.

이번 Step에서는 코드를 이식하지 않습니다.

기준:

- S8RPKCheats `main`: `96dfc11508bb9bfdc429f656f15530b13cb56045`
- 분석 브랜치: `research/san8rpk-viewer-analysis`
- Viewer EXE SHA-256:
  `34abf52f9651d4313076b16042476e5646967aa55af65613f542d69883084c3d`

---

# 1. 분류 기준

이 문서에서 기능별 이식 상태를 네 종류로 분류합니다.

### A. 기존 기능 대체 필요

Viewer 패치와 현재 S8RPKCheats가 **같은 코드 바이트를 직접 수정**하거나, 같은 흐름을 서로 다른 방식으로 재구성합니다.

동시에 사용하지 않고 하나를 선택해야 합니다.

### B. 기능 목적 중복 - 비교 후 선택

주소는 겹치지 않지만 같은 AI 판단을 서로 다른 방식으로 바꿉니다.

기술적으로 동시에 적용 가능하더라도 과보정 위험이 있어 A/B 테스트가 필요합니다.

### C. 독립 이식 가능

현재 S8RPKCheats와 직접 주소 충돌이 확인되지 않고 기능 목적도 별개입니다.

그래도 원본 바이트 검증과 런타임 테스트는 필요합니다.

### D. 재설계 필수

Viewer 자체 정적 구조에서 hook overlap 또는 제어 흐름 위험이 확인되어 그대로 복사하면 안 됩니다.

# 3. 현재 S8RPKCheats AI 전투 개선

기준 파일:

```text
Internal DX11 Base/Cheats/War/Roadblock.cpp
```

현재 세 패치:

| 기능 | RVA | 원본 | 적용 |
|---|---:|---|---|
| 복수 공격 분기 | `+144D24C` | `74 0A` | `EB 0A` |
| 주인공 대상 호전성 증가 분기 제거 | `+1464B91` | `75 1E` | `90 90` |

- 매우 단순

- 세 주소 전체 사전 검증
- 부분 실패 시 rollback

Viewer를 이식하더라도 이 안전 구조는 유지할 가치가 있습니다.

# 4. 공격 후보 확장 - 기존 +144D24C를 대체해야 함

Viewer:

```text
hook +144D248 ~ +144D257
```

현재:

```text
patch +144D24C ~ +144D24D
```

현재 패치는 Viewer 16-byte hook 범위 안에 완전히 들어갑니다.

따라서:

```text
Viewer 공격 cave + 현재 +144D24C
```

동시 적용은 불가능합니다.

## 이식 방향

Viewer 공격 후보 확장을 채택한다면:

- 기존 `kAIWarMultiAttack` 패치 제거/비활성화
- `+144D248` cave 방식으로 교체
- 기존 AI 전투 개선 토글 안에 넣을지 별도 토글로 분리할지 결정

권장 조사 단계에서는 별도 토글로 먼저 검증하는 것이 안전합니다.

예:

```text
[AI 공격 후보 확장 - 실험]
```

런타임 확인 후 기존 첫 패치를 대체합니다.

# 5. 플레이어 우선 제거 - 주소 충돌은 없지만 기능 중복 가능

Viewer:

```text
+144BB60
add rsi, 13,600,000,000 -> NOP

+144BC8B
add rsi, 1,700,000,000 -> NOP
```

현재:

```text
+1464B91
jne +1E -> NOP NOP
```

주소는 완전히 다릅니다.

따라서 **byte-level 직접 충돌은 없습니다.**

하지만 두 기능 모두 현재 해석상 플레이어에 대한 특수 호전/우선 판단을 완화합니다.

## 위험

둘을 동시에 켜면:

- Viewer가 수치 가산을 제거
- 현재 패치가 별도 조건분기까지 제거

하여 플레이어 편향을 필요 이상으로 제거할 수 있습니다.

## 이식 검증 순서

1. 현재 `+1464B91` 단독
2. Viewer `+144BB60` 단독
3. Viewer `+144BC8B` 단독
4. Viewer A+B
5. Viewer A+B + 현재 `+1464B91`

비교 후 최소한의 변경만 유지하는 것이 좋습니다.

---

# 6. 공백지 점령 패치는 현재 기능 유지 후보

현재 S8RPKCheats:

```text
+145BDAB
B8 01 00 00 00
->
B8 00 00 00 00
```

Viewer 최종 profile에서 같은 RVA에 대한 직접 patch는 확인되지 않았습니다.

따라서 Viewer 공격 기능을 옮긴다고 해서 이 패치를 자동 제거할 근거는 없습니다.

## 현재 판단

`+145BDAB`은:

- Viewer 공격 후보 확장과 직접 중첩 없음
- Viewer 플레이어 우선 NOP와 중첩 없음

이므로 **우선 유지한 상태로 Viewer 공격 로직을 비교**하는 것이 맞습니다.

단 Viewer cave가 간접적으로 공백지 선택까지 개선하는지 런타임에서 확인되면 나중에 중복 여부를 다시 판단합니다.

# 7. AI 포로 판정과 도독 포로 직접 처분은 별개

Viewer AI 포로:

```text
+1E52A8D
+1E54190
```

현재 도독 포로 기능:

```text
+1E53BB2  main hook
+1E53BBB  allow
+1E540B7  deny
+1E5CE39  collect call
+1E5DE47  relations call
```

주소가 서로 다릅니다.

기능 목적도 다릅니다.

### Viewer

AI가 자동으로 포로를:

- 석방할지
- 처형할지

판정하는 공식 변경.

### 현재 S8RPKCheats

플레이어 측 도독이 승전 포로를 직접 처분할 수 있도록 UI/권한 흐름을 확장.

따라서 두 기능은 **병행 가능성이 높습니다.**

# 8. 공유 global +2E98BC8은 충돌이 아니다

Viewer 여러 payload와 현재 `GovernorPrisonerDisposal.cpp` 모두:

```text
SAN8RPK.exe + 0x02E98BC8
```

을 사용합니다.

현재 코드 명칭:

```cpp
kGlobalPtrOffset = 0x02E98BC8;
```

Viewer reader/profile에서도 manager/global root로 사용합니다.

하지만 둘 다 이 주소의 **포인터를 읽어 context를 찾는 용도**입니다.

따라서:

```text
같은 global 주소 사용 == hook 충돌
```

이 아닙니다.

충돌 여부는:

- 해당 주소 자체를 overwrite하는지
- 같은 instruction range를 patch하는지

로 판단해야 합니다.

현재 확인상 `+2E98BC8`은 공유 read context입니다.

# 9. 포로 메시지 상세화 - 독립 이식 후보

Viewer 4 patch:

```text
+1E599BE
+1E5A82C
+1E5BA1F
+1E5BA4B
```

현재 S8RPKCheats에서 직접 사용하는 주소:

- 도독 main: `+1E53BB2`
- deny: `+1E540B7`
- collect: `+1E5CE39`
- relations: `+1E5DE47`

직접 중첩이 없습니다.

또 메시지 profile은:

```text
display-only
no code cave
no decision changes
```

입니다.

## 이식 난이도

현재 분석 기능 중 가장 낮은 편입니다.

필요한 것:

- 4개 원본 바이트 검증
- 4개 replacement 적용
- disable 시 원복

뿐입니다.

따라서 나중에 Viewer 기능을 실제 옮길 때 **첫 구현 후보**로 적합합니다.

# 10. 결전 1년 gate와 현재 전기 기능

Viewer:

```text
+1335961
+132E4BD
```

현재 `TengiCave.cpp`는 fixed RVA가 아니라 AOB:

```text
41 88 87 18 4B 1E 00
```

를 검색해 전기 데이터 주소를 캡처합니다.

현재 전기 기능의 목적:

- 전기 데이터 주소 캡처
- 게이지 읽기/쓰기
- 발생 플래그 관리

Viewer 결전 기능의 목적:

- 특정 TotalWarPoint 계산 시 retry 값만 1로 override

현재 확인 범위에서는 동일 instruction range라는 증거가 없습니다.

## 분류

**독립 기능**.

단 나중에 두 기능을 동시에 켠 테스트는 필요합니다.

전기 게이지를 강제로 변경하는 기능과 결전 retry gate는 논리적으로 서로 영향을 줄 수 있기 때문입니다.

이건 메모리 hook 충돌이 아니라 **게임 규칙 상호작용**입니다.

# 11. 항복권고 실패 로직 - 가장 주의가 필요한 부분

Viewer:

```text
PRE  +1451EAD
POST +1451ECD
```

PRE가 active record를 찾으면:

```text
jmp +1451ED9
```

하지만 POST hook이 덮는 범위:

```text
+1451ECD ~ +1451EDC
```

즉 `+1451ED9`가 POST trampoline의 **중간**에 들어갑니다.

이건 현재 Viewer 정적 구조 자체에서 발견된 위험입니다.

## 분류

**D - 재설계 필수**

Viewer 바이트를 그대로 옮기지 않습니다.

---

# 12. 항복권고 PRE/POST 안전 재설계 후보

원래 `+1451ED9`에서 시작하는 명령은:

```asm
mov rbx,[r14+10h]
```

으로 분석됐습니다.

따라서 Viewer가 의도한 skip 의미가 맞다면 안전한 후보는:

```asm
; active refusal record 발견
stats.skipped++

mov rbx,[r14+10h]   ; 원래 +1451ED9 instruction 직접 재현
jmp +1451EDD        ; POST hook 범위 뒤
```

입니다.

하지만 이건 **아직 구현하지 않는 설계 후보**입니다.

실제 이식 전:

- PRE/POST 원본 함수 전체 흐름 확인
- 해당 분기 런타임 레지스터 검증

이 먼저 필요합니다.

---

# 13. 항복권고 공격 boost는 공격 cave와 결합됨

Viewer의:

```text
항복권고 실패 -> 3개월 record -> attack score ×5
```

기능은 독립된 한 주소 patch가 아닙니다.

record 생성은 `+1451ECD` 쪽이지만 실제 ×5는 Step 03의:

```text
+144D248 attack cave
```

안에서 실행됩니다.

따라서 Viewer 공격 후보 확장을 이식하지 않고 항복권고 boost만 옮기려면:

- 현재 바닐라 score 경로에 별도 hook 추가
- 또는 Viewer attack cave의 refusal 부분만 별도 설계

가 필요합니다.

## 결론

항복 실패 공격 boost는 **Viewer 공격 후보 확장과 기술적으로 결합도가 높음**.

나중에 하나의 `AI 전략 개선` 모듈 안에 같이 넣는 편이 구조상 자연스럽습니다.

# 14. 고의리 군주 항복 억제는 독립 가능

Viewer:

```text
+193C86E
```

이 hook은 다른 Viewer 공격/포로 cave와 별개로:

- 대상 force의 군주
- 군주 의리
- XMM6 score

만 확인해 최종 score를 보정합니다.

현재 S8RPKCheats에서 동일 RVA를 사용하는 기능은 확인되지 않았습니다.

따라서 이 기능은 **독립적인 별도 토글**로 옮기기 쉽습니다.

예:

```text
AI 고의리 군주 항복 억제
```

다만 XMM6가 정확한 확률인지 평가점수인지 런타임 확인 후 사용자 설명 문구를 결정하는 것이 안전합니다.

# 15. 기술적 이식 난이도 분류

| 기능 | 난이도 | 이유 |
|---|---|---|
| AI 포로 결과 메시지 상세화 | 낮음 | fixed-size 4 patch, cave 없음 |
| 결전 1년 retry | 낮음~중간 | 작은 동일 cave 2개 |
| 고의리 군주 항복 억제 | 중간 | 단일 cave, 구조 명확 |
| 플레이어 우선 가산 제거 | 낮음 | 2 static NOP, 다만 의미 A/B 검증 필요 |
| AI 포로 판정 | 중간~높음 | 긴 cave + 여러 native helper |
| 공격 후보 확장 | 높음 | 기존 패치와 직접 충돌, score/relation 재구성 |
| 항복 실패 공격 전환 | 높음 | record + PRE/POST + attack cave 결합 |
| 항복 PRE/POST 그대로 복제 | 금지 | hook overlap 위험 |

# 16. 추천 이식 순서

분석 자료만 기준으로 가장 안전한 순서는:

### Phase 1 - 독립/저위험

1. 포로 결과 메시지 상세화
2. 결전 1년 retry
3. 고의리 군주 항복 억제

각각 별도 토글로 런타임 확인.

### Phase 2 - 기존 AI 전투 개선 비교

4. Viewer 플레이어 우선 가산 제거 A/B
5. 기존 `+1464B91`과 비교
6. Viewer 공격 후보 확장 테스트
7. 기존 `+144D24C`와 대체 여부 결정
8. `+145BDAB` 공백지 패치는 일단 유지하며 비교

### Phase 3 - AI 포로

9. AI 포로 판정 read-only 진단
10. 포로/군주 레지스터 의미 확인
11. 실제 처형 결과와 공식 대조
12. write hook 적용

### Phase 4 - 항복권고 실패 전환

13. PRE/POST 원본 함수 흐름 추가 확인
14. overlap 안전 재설계
15. record만 먼저 진단
16. 재권고 차단
17. attack score ×5
18. 최종 통합

# 17. UI 구조 후보

나중에 구현할 때 Viewer의 기능을 하나의 거대한 체크박스에 전부 묶는 것보다 S8RPKCheats 스타일로 세분화하는 편이 검증과 원복에 유리합니다.

예시:

```text
[AI 전략]
□ AI 공격 후보 확장
□ 플레이어 우선 가산 제거
□ AI 포로 판정 개선
□ AI 고의리 군주 항복 억제
□ 항복권고 실패 시 공격 우선

[전쟁/메시지]
□ AI 포로 결과 상세 표시

[전기]
□ 결전 재시도 1년
```

기존:

```text
AI 전투 개선
```

은 Viewer 공격 로직 검증이 끝난 후:

- 기존 3패치 유지형
- Viewer 방식 통합형

중 어느 쪽으로 정리할지 결정하면 됩니다.

---

# 18. 원본 검증 정책

Viewer는 단순 원본 바이트 비교뿐 아니라 주변 함수 SHA-256 guard까지 사용합니다.

S8RPKCheats에서도 최소한 다음은 유지해야 합니다.

1. hook 대상 원본 바이트 확인
2. 이미 우리 패치가 들어간 경우 구분
3. 다른 값이면 적용 거부
4. 여러 patch를 한 토글로 묶을 경우 **전부 사전 검증**
5. 쓰기 실패 시 이번 호출 변경분 rollback

특히 Viewer 기능을 여러 개 동시에 옮기면 같은 함수군이 많아지므로, 단순히 “주소가 맞으니까 쓰기”로 가면 안 됩니다.

# 19. 공유 code cave 설계 여부

Viewer는 하나의 AIController에서 큰 `0x3000` cave를 할당하고:

- attack
- prisoner
- refusal pre/post
- hatred classifier
- surrender
- stats/record table

를 한 덩어리로 관리합니다.

S8RPKCheats에서는 처음부터 이렇게 크게 묶을 필요는 없습니다.

## 장점 - 분리형

- 기능별 토글/검증 쉬움
- 문제 발생 시 원인 분리 쉬움
- 기존 기능과 점진적 병행 가능

## 단점

항복 실패 record처럼 서로 공유해야 하는 데이터가 생기면 별도 shared state가 필요합니다.

## 추천

초기 이식은 **기능별 cave 분리**.

나중에 충분히 검증된 뒤 AI 전략 기능만 하나의 전용 모듈로 합치는 쪽이 안전합니다.

# 20. 현재 기능과 Viewer 기능의 관계를 최종 정리

## 현재 AI 전투 개선에서 남길 가능성이 높은 것

```text
+145BDAB 공백지 점령 제한 완화
```

Viewer에 동일 직접 patch가 확인되지 않았기 때문입니다.

## Viewer가 대체할 가능성이 높은 것

```text
+144D24C 복수 공격 branch
```

Viewer `+144D248` cave가 더 넓고 명시적인 후보/score 로직을 수행합니다.

## 비교 후 하나만 남길 가능성이 높은 것

```text
현재 +1464B91
vs
Viewer +144BB60/+144BC8B
```

목적이 겹칠 가능성이 큽니다.

## 완전히 새 기능

- AI 포로 판정
- AI 포로 결과 메시지 상세화
- 결전 retry 1년
- 고의리 군주 항복 억제
- 항복권고 실패 후 공격 우선

# 21. 가장 먼저 이식해도 되는 후보

정적 분석만 놓고 보면 가장 독립성이 높은 것은:

### 1순위

```text
AI 포로 결과 메시지 상세화
```

이유:

- decision 변경 없음
- code cave 없음
- 현재 기능과 주소 충돌 없음
- A/B 확인 쉬움

### 2순위

```text
결전 재시도 1년
```

이유:

- 핵심 로직이 매우 짧음
- 다른 결전 조건 유지
- 현재 전기 hook과 직접 중첩 미확인

### 3순위

```text
고의리 군주 항복 억제
```

이유:

- 단일 hook
- 공식 명확
- 독립 적용 가능

이 순서는 “좋은 기능 순위”가 아니라 **기술적으로 분리해서 검증하기 쉬운 순서**입니다.

# 22. 반드시 마지막에 다룰 기능

```text
항복권고 실패 후 공격 우선 전환
```

이유:

- PRE/POST 두 hook
- 3개월 record
- native 전환 call
- attack cave와 데이터 공유
- Viewer 내부 overlap 위험 존재

따라서 공격 후보 확장과 refusal 흐름을 충분히 이해한 뒤 마지막에 다루는 것이 맞습니다.

# 23. Step 09 결론

현재 S8RPKCheats와 Viewer는 완전히 별개의 AI 개선이 아닙니다.

특히 공격 부분은:

```text
현재 +144D24C
Viewer +144D248
```

로 같은 원본 흐름을 직접 공유합니다.

따라서 Viewer 공격 로직을 채택한다면 현재 AI 전투 개선을 단순히 “추가”하는 게 아니라 **일부 교체**해야 합니다.

반면:

- AI 포로 판정
- 메시지 상세화
- 결전 1년
- 고의리 군주 항복 억제

는 현재 코드와 독립성이 높습니다.

그리고 항복권고 실패 전환은 Viewer 자체 overlap 위험 때문에 **그대로 이식하지 않고 재설계**해야 합니다.

이 문서를 이후 실제 구현 작업의 기준 지도으로 사용합니다.
