# Step 04 - 플레이어 우선공격 제거 상세 해부

## 0. 이번 Step의 범위

이 문서는 Viewer 상태창에 표시되는:

```text
공격·포로 AI 켜짐 (플레이어 우선 가산 제거)
```

가 실제로 어떤 패치와 연결되는지 분석한 기록입니다.

비교 대상은 현재 S8RPKCheats의:

```text
SAN8RPK.exe + 0x1464B91
75 1E -> 90 90
```

입니다.

이번 Step에서는 **주소/원본 바이트/치환 바이트/패치 설치 방식**까지는 확정합니다.

단, 대상 게임 `SAN8RPK.exe`의 해당 함수 전체 디스어셈블리는 현재 분석 자료에 포함되어 있지 않으므로:

- 두 Viewer 패치 중 어느 것이 '호전'인지
- 어느 것이 '극호전'인지
- `rsi`가 게임 내부에서 정확히 어떤 이름의 점수 변수인지

는 아직 확정하지 않습니다.

## 1. Viewer가 직접 표시하는 기능명 - 확정

Viewer의 `show_ai_status()`에는 다음 문자열이 직접 포함되어 있습니다.

```text
공격·포로 AI 켜짐 (플레이어 우선 가산 제거)
· 추가 후보 %d / 갱신 %d
· 석방 %d / 처형 %d
· 권고 실패 %d / 전환 %d / 재권고 차단 %d
```

따라서 **'플레이어 우선 가산 제거'라는 표현은 게시글만의 설명이 아니라 Viewer 프로그램 자체의 기능명**입니다.

---

## 2. Viewer AI profile의 static patch 2개 - 확정

`ai_profile`은 `STATIC_PATCHES = {}`를 만든 뒤 두 패치를 `HOOKS`에 추가합니다.

### Patch A

RVA:

```text
SAN8RPK.exe + 0x0144BB60
```

원본 13 bytes:

```text
48 B8 00 88 9F 2A 03 00 00 00 48 03 F0
```

x86-64 해석:

```asm
movabs rax, 0x000000032A9F8800
add    rsi, rax
```

10진수:

```text
0x32A9F8800 = 13,600,000,000
```

적용:

```text
90 90 90 90 90 90 90 90 90 90 90 90 90
```

즉 위 두 명령을 통째로 제거합니다.

---

### Patch B

RVA:

```text
SAN8RPK.exe + 0x0144BC8B
```

원본 7 bytes:

```text
48 81 C6 00 F1 53 65
```

x86-64 해석:

```asm
add rsi, 0x6553F100
```

10진수:

```text
0x6553F100 = 1,700,000,000
```

적용:

```text
90 90 90 90 90 90 90
```

즉 이 가산도 제거합니다.

---

## 3. 두 가산값의 관계 - 확정

두 값은 정확히 8배 관계입니다.

```text
1,700,000,000 × 8 = 13,600,000,000
```

즉 Viewer는 같은 `rsi`에 들어가는 **서로 다른 크기의 두 양수 가산**을 제거합니다.

이 자체로는 두 분기의 게임 명칭을 알 수 없지만, 동일 종류의 우선도/점수 가중치가 두 단계로 존재한다는 해석과 매우 잘 맞습니다.

---

## 4. 이 두 patch가 실제로 설치되는 방식 - 확정

`ai_profile` Python bytecode에서 다음 구조를 직접 복원했습니다.

개념적으로:

```python
STATIC_PATCHES = {}

HOOKS.append((
    0x144BB60,
    bytes.fromhex("48b800889f2a030000004803f0"),
    -1,
))
STATIC_PATCHES[-1] = bytes.fromhex(
    "90909090909090909090909090"
)

HOOKS.append((
    0x144BC8B,
    bytes.fromhex("4881c600f15365"),
    -2,
))
STATIC_PATCHES[-2] = bytes.fromhex(
    "90909090909090"
)
```

`ai_patch.AIController._patch_bytes()`는:

1. `offset`이 `STATIC_PATCHES`에 있으면
2. code cave jump를 만들지 않고
3. 해당 static replacement 바이트를 그대로 반환합니다.

따라서 `-1`, `-2`는 cave offset이 아니라 **static replacement를 선택하기 위한 내부 key**입니다.

`AIController._exchange()`는 이 항목들도 일반 hook과 동일하게:

- 현재 바이트가 예상 원본인지 확인
- 메모리 보호 변경
- replacement 쓰기
- instruction cache flush
- 쓰기 후 재검증
- 실패 시 이전 변경분 롤백
- 기능 해제 시 원본 복구

절차를 거칩니다.

즉 두 NOP는 일시적인 실험용 쓰기가 아니라 **Viewer AI 기능의 정식 구성요소**입니다.

---

## 5. 왜 이 두 NOP가 '플레이어 우선 가산 제거'로 보이는가

### 직접 확인된 사실

1. Viewer 자체가 활성 상태를 **'플레이어 우선 가산 제거'**라고 표시합니다.
2. AI profile이 code cave 외에 별도 static patch로 제거하는 코드는 정확히 두 군데입니다.
3. 두 원본 명령 모두 `rsi`에 큰 **양의 값**을 더합니다.
4. 적용 시 해당 가산 명령 전체를 NOP 처리합니다.
5. 두 가산값은 서로 8배 차이입니다.

### 게시글 설명

사용자 제공 설명에는:

- AI 호전도가 `호전`, `극호전`일 때
- 플레이어가 인접하면 다른 목표보다 플레이어를 과도하게 우선했고
- 변경 후에는 약한 세력을 우선하도록 했으며
- 플레이어가 실제로 가장 약하면 공격 대상이 될 수 있다고 설명합니다.

### 현재 판단

위 두 자료를 합치면:

> `+144BB60`, `+144BC8B`의 두 가산 제거가 호전/극호전 계열의 플레이어 우선 보너스를 없애는 패치

일 가능성이 **매우 높습니다.**

하지만 현재 Viewer EXE에는 원본 게임 함수의 전체 주변 명령이 들어 있지 않으므로, 이 문서에서는 이를 **유력**으로 분류합니다.

특히 다음은 아직 미확정입니다.

- A가 호전인지 극호전인지
- B가 호전인지 극호전인지
- 가산 전후의 `rsi` 변수의 정확한 게임 내부 명칭
- 가산 조건에서 플레이어 세력 여부를 판정하는 앞쪽 분기

## 6. 현재 S8RPKCheats 방식 - 확정

현재 파일:

```text
Internal DX11 Base/Cheats/War/Roadblock.cpp
```

현재 프로젝트는 다음 패치를 사용합니다.

```text
SAN8RPK.exe + 0x1464B91

원본:
75 1E

적용:
90 90
```

명령어 차원에서는:

```asm
jne +0x1E
```

를 제거해서 **항상 fall-through**하도록 만드는 변경입니다.

현재 프로젝트 코드에서 이 패치의 이름은:

```text
kAIWarHeroAggro
```

이고 UI 설명은:

```text
주인공 대상 호전성 증가 분기 제거
```

입니다.

여기서 '주인공 대상 호전성 증가'라는 의미는 **현재 S8RPKCheats가 이 주소에 부여하고 있는 기능 의미**입니다.

이번 Step에서는 `+1464B91` 주변 원본 함수 전체를 확보하지 않았으므로, 해당 의미를 Viewer 분석만으로 다시 독립 검증한 것은 아닙니다.

## 7. Viewer와 S8RPKCheats는 같은 주소를 쓰지 않는다 - 확정

Viewer `ai_profile`의 최종:

- `HOOKS`
- `STATIC_PATCHES`
- `GUARDS`
- payload fixup 정수

를 확인한 결과:

```text
+1464B91
```

은 존재하지 않습니다.

반대로 현재 S8RPKCheats는:

```text
+144BB60
+144BC8B
```

을 수정하지 않습니다.

즉 양쪽은 **같은 목적을 서로 다른 위치/방식으로 해결하고 있습니다.**

## 8. 구현 방식 차이

### 현재 S8RPKCheats

```text
+1464B91
75 1E -> 90 90
```

특징:

- 2-byte 조건분기 제거
- 제어 흐름 자체를 바꿈
- 해당 조건이 false/true일 때 갈라지던 경로를 한쪽으로 고정

### Viewer

```text
+144BB60
add rsi, 13,600,000,000 -> NOP

+144BC8B
add rsi, 1,700,000,000 -> NOP
```

특징:

- 분기 구조는 그대로 둠
- 특정 경로에서 더해지던 **수치 가산만 제거**
- 후보 자체를 제거하는 방식이 아니라면 플레이어는 여전히 일반 후보로 남을 수 있음

이 마지막 점은 게시글의:

> 플레이어 세력이 가장 약하다면 공격 받을 가능성은 있습니다.

설명과 Viewer 방식이 잘 맞는 이유입니다.

단, '플레이어가 일반 후보로 남는다'는 결론은 Step 03의 후보 확장 흐름과 이번 static patch 형태를 합친 해석이며, 실제 게임 런타임 검증 전까지는 **유력**으로 둡니다.

## 9. Step 03과 합쳐서 보면

Viewer AI 공격 개선은 최소 두 층으로 나뉩니다.

### 층 1 - 후보 제한 해제

`+144D248` code cave:

- 기존 목표 A/B 밖 세력도 후보에 포함
- 동일한 score 경쟁 수행
- 기존 목표 A는 1.1배 우대

### 층 2 - 플레이어 특수 가산 제거

`+144BB60`, `+144BC8B` static NOP:

- 두 개의 큰 양수 가산을 제거
- Viewer 자체 표현은 '플레이어 우선 가산 제거'

따라서 게시글의 두 설명:

1. 목표세력 외 국가도 공격
2. 호전/극호전 시 플레이어만 과도하게 우선하는 현상 제거

는 **서로 다른 패치 층**으로 구현되어 있는 것으로 보입니다.

---

## 10. 현재 우리 AI 전투 개선과의 실질적 차이

| 항목 | S8RPKCheats 현재 | Viewer |
|---|---|---|
| 목표세력 외 후보 | `+144D24C` 분기 강제 | `+144D248` cave에서 명시적으로 후보/score 재구성 |
| 플레이어 우선 처리 | `+1464B91` 조건분기 제거 | `+144BB60`, `+144BC8B` 두 수치 가산 제거 |
| 공백지 보완 | `+145BDAB` 별도 패치 | 같은 주소 패치 없음 |
| 플레이어 특수 가산을 숫자로 제거 | 없음 | 있음 |
| 호전/극호전 2단계로 보이는 별도 가산 | 없음 | 두 patch 존재 |
| 구현 성격 | 간단한 직접 branch/immediate 패치 | cave + 별도 static score patch 조합 |

따라서 기능 이름은 비슷하지만 **Viewer 쪽이 더 세분화된 AI score 수정**입니다.

## 11. 주소 충돌과 기능 충돌은 구분해야 한다

### 주소 충돌

`+1464B91`과 Viewer 두 static patch는 주소가 다르므로 직접적인 byte overlap은 없습니다.

즉 기술적으로는 세 패치를 동시에 쓸 수 있습니다.

### 기능 충돌

하지만 목적이 모두 '플레이어 편향 완화'라면 동시에 적용할 경우:

- Viewer가 플레이어 bonus를 제거한 뒤
- 우리 `+1464B91` 분기 제거까지 추가로 적용

되어 **의도보다 더 크게 AI 판단을 바꿀 가능성**이 있습니다.

따라서 나중에 Viewer 방식을 이식할 때는 처음부터 합치지 말고:

1. 현재 `+1464B91` 단독
2. Viewer 두 NOP 단독
3. Step 03 후보 확장 + Viewer 두 NOP
4. 필요할 때만 현재 `+1464B91` 추가

순서로 A/B 비교하는 것이 안전합니다.

## 12. 런타임 검증 시 확인할 것

Viewer 방식 이식 여부를 판단하려면 아래 케이스가 좋습니다.

### 시나리오

- AI 군주 호전도 '호전'
- AI 군주 호전도 '극호전'
- 플레이어가 AI와 인접
- 동시에 AI 주변에 더 약한 AI 세력이 존재

### 비교 항목

- 플레이어를 무조건 고르는지
- 더 약한 AI 세력을 선택하는지
- 플레이어가 실제로 가장 약한 경우에는 다시 플레이어를 공격하는지
- 호전과 극호전에서 결과 차이가 있는지

### 진단 권장

두 NOP를 한꺼번에 확정하지 말고:

- Patch A만
- Patch B만
- A+B

세 단계로 나눠 로그를 보는 것이 좋습니다.

그렇게 해야 어느 주소가 호전/극호전에 해당하는지 실제 게임에서 확정할 수 있습니다.

## 13. Step 04 결론

### 확정

- Viewer는 `+1464B91`을 사용하지 않습니다.
- Viewer AI profile에는 두 개의 static NOP patch가 있습니다.
- 둘 다 `rsi`에 큰 양수를 더하는 원본 코드를 제거합니다.
- 값은 13,600,000,000과 1,700,000,000이며 정확히 8배 차이입니다.
- Viewer UI는 활성 기능을 직접 **'플레이어 우선 가산 제거'**라고 부릅니다.
- static patch는 일반 hook과 같은 검증/쓰기/원복 절차로 설치됩니다.

### 유력

- 두 static patch가 게시글의 호전/극호전 플레이어 우선 공격 보너스를 각각 제거하는 코드.
- 이 방식은 플레이어를 공격 후보에서 제외하기보다 **특별 가산만 제거**하기 때문에 '플레이어가 가장 약하면 공격 가능'이라는 설명과 부합.

### 미확정

- 두 주소 각각의 호전/극호전 매핑.
- `rsi` 점수의 정확한 내부 명칭.
- 현재 우리 `+1464B91`이 Viewer 두 NOP와 비교해 어느 범위까지 같은 효과를 내는지.

이 세 항목은 실제 `SAN8RPK.exe` 주변 디스어셈블리 또는 게임 A/B 진단으로 확정해야 합니다.
